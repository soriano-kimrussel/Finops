# QuickBooks Online integration

FinOps HQ imports customers, invoices and payments from QuickBooks Online and reconciles them against its own books.

## Status

| Part | State |
|---|---|
| Simulated mode (default) | Implemented and tested end to end, including in the Playwright suite. |
| Live mode: OAuth 2.0, token refresh, paged queries, rate-limit and error handling, webhook signatures | Implemented against Intuit's documented API. Unit-tested with recorded response shapes and fake transports. **Not yet run against a real Intuit sandbox company**, because no credentials were available. Treat it as untested until you have done that. |

## Modes

Set `QUICKBOOKS_MODE` in `.env`.

### `simulated`

No network calls are made. The adapter (`internal/quickbooks/simulated.go`) builds QuickBooks-shaped records from the organization's own data and introduces deliberate, repeatable differences:
- every ninth invoice is 25.00 higher
- every seventh invoice is dated two days later
- every eleventh invoice is missing
- two extra invoices and a customer, "Westfield Legal Partners", exist only in "QuickBooks"
- a few payments differ by 10.00

Every simulated record carries `"simulated": true` in its stored payload. The connection is stored with `mode = 'simulated'`, and the Integrations page, imported records and dashboard all label it.

### `live`

Requires an Intuit developer app.

1. Create an app at https://developer.intuit.com and add the **Accounting** scope.
2. Under *Keys & credentials → Development*, copy the client ID and secret.
3. Add the redirect URI `http://localhost:5173/api/integrations/quickbooks/callback`. The Vite dev server proxies `/api` to the Go API; in production use your public URL.
4. Fill in `.env`:
   ```
   QUICKBOOKS_MODE=live
   QUICKBOOKS_ENVIRONMENT=sandbox
   QUICKBOOKS_CLIENT_ID=...
   QUICKBOOKS_CLIENT_SECRET=...
   QUICKBOOKS_REDIRECT_URL=http://localhost:5173/api/integrations/quickbooks/callback
   ```
5. Restart `serve`, open **Integrations** and click **Connect QuickBooks**. Sign in with a sandbox company.

## OAuth flow

1. `POST /api/orgs/{org}/integrations/quickbooks/connect` (requires `integrations.manage`) creates a random 32-byte state secret. Only its SHA-256 is stored, with the user and a 10-minute expiry. The response is Intuit's authorization URL, with `state = <organization id>.<secret>`.
2. Intuit redirects to `GET /api/integrations/quickbooks/callback?code&state&realmId`. The session cookie comes along (SameSite=Lax permits it on this top-level navigation). The server:
   - checks the user is still a member who may manage integrations
   - consumes the state, which must be unused, unexpired and belong to the same user
   - exchanges the code for tokens
   - stores both tokens encrypted
   - writes an audit entry and redirects back to the Integrations page
3. A QuickBooks company (realm) can be connected to only one organization at a time (unique index).

## Token storage and refresh

- Access and refresh tokens are encrypted with **AES-256-GCM** using `TOKEN_ENCRYPTION_KEY` (32 random bytes, generated by `setup-db.ps1`). The organization id is the authenticated associated data, so a ciphertext copied onto another tenant's row fails to decrypt.
- Access tokens last about an hour. Before each sync, and again after any 401, the worker refreshes the token if it expires within two minutes. The refresh happens while the connection row is locked (`SELECT … FOR UPDATE`). Intuit **rotates refresh tokens**, so two workers refreshing at once would invalidate each other's token; the lock prevents that, and the new refresh token is stored before the access token is used.
- If Intuit rejects the refresh token (revoked, or older than about 100 days), the connection is marked `needs_reauth`, the job fails without retrying, and the UI offers **Reconnect**.
- Disconnecting revokes the token with Intuit (best effort) and deletes it locally. Imported records and reconciliation history are kept.

## Fetching data

- Endpoint: `GET {base}/v3/company/{realmId}/query?query=SELECT * FROM {Entity} STARTPOSITION n MAXRESULTS m&minorversion=75`, where base is `sandbox-quickbooks.api.intuit.com` or `quickbooks.api.intuit.com`.
- Pages of 100 are fetched until a short page comes back. The worker extends its job lease after every page.
- **HTTP 429:**
  - Wait `Retry-After` seconds, or exponential backoff with jitter if the header is missing, and retry up to 3 times.
  - If it is still throttled, the job is rescheduled with the worker's backoff (30 s, 60 s, … up to 30 minutes).
- **HTTP 5xx and network errors** are retried in the same way, then marked transient.
- **HTTP 400 faults** (`{"Fault":{"Error":[{"code","Message","Detail"}]}}`) fail the job with the fault message, since retrying wouldn't help.
- Amounts are decoded from the JSON number text straight into `decimal.Decimal`, so no float is involved.

## Validation and import

Every incoming record is validated:
- **IDs:** each record has an id, invoices have a customer, and payments have a positive amount.
- **Balances:** an invoice balance is between 0 and its total, and a payment is not applied for more than its total.
- **Currencies:** must be supported, and amounts must fit the currency.

Invalid records are counted as *rejected* in the job's stats, with up to ten example messages shown in the job details, and are never stored.

- **Customers** are linked to an existing customer if one already carries the same QuickBooks id, otherwise to one with exactly the same name. Failing both, they are created as `source = 'quickbooks'` customers. Customer details entered in FinOps HQ are never overwritten.
- **Invoices and payments** are stored in `external_records`, unchanged and keyed by QuickBooks id. A payment applied to several invoices becomes one record per invoice. Records are rewritten only when their content hash changes, so re-running a sync is a no-op.
- They **never** change invoices or payments in the books. Differences go to reconciliation (below), where a person decides.

## Reconciliation

Reconciliation runs after every sync that imports invoices or payments, and on demand from the Reconciliation page.

- **Invoices** match first through an import link: an invoice created from a QuickBooks record during reconciliation. Failing that, they match by document number. A matched pair is then compared: a different amount or currency gives *amount differs*; a different issue date gives *date differs*.
- **Payments** are matched within their matched invoice. The best candidate is the same amount on the same date, then the same amount on another date, then the payment closest in date.
- Whatever is left on either side becomes *only in QuickBooks* or *only in FinOps HQ*. Nothing is flagged until something has been imported, so an empty QuickBooks company doesn't flag every invoice.

Each result is stored with a fingerprint of the compared values. An unchanged result keeps its record, including any decision already made. If the values change, the old record is marked *superseded* and a new open one created, so the full history of a difference and every decision about it is preserved.

Reviewers (`reconciliation.review`) can record these decisions:

| Difference | Allowed decisions |
|---|---|
| Amount or date differs | accept difference, needs follow-up, ignore |
| Only in FinOps HQ | accept, needs follow-up, ignore |
| Only in QuickBooks (invoice) | **create invoice from QuickBooks**, needs follow-up, ignore |
| Only in QuickBooks (payment) | needs follow-up, ignore |

Every decision except *create invoice* needs a note. Decisions are final, except that a follow-up can later be resolved. The database refuses edits to recorded decisions. *Create invoice from QuickBooks* creates a sent invoice in FinOps HQ from the QuickBooks total (tax included, as one line) and links it, so the next run matches it. Every decision is audited.

## Webhooks

`POST /api/webhooks/quickbooks` accepts Intuit change notifications.

- The `intuit-signature` header must equal base64(HMAC-SHA256(body, `QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN`)). Anything else gets 401.
- For each notified realm with an active connection, a full sync is queued.
- The job's idempotency key is derived from the payload hash, so Intuit's redeliveries don't queue twice. If a sync for that connection is already queued or running, it is reused.

Webhooks need a URL Intuit can reach. A local machine can't receive them without a tunnel, so this part has been verified only by the automated tests.

## Configuration reference

| Variable | Meaning |
|---|---|
| `QUICKBOOKS_MODE` | `simulated` (default) or `live` |
| `QUICKBOOKS_ENVIRONMENT` | `sandbox` (default) or `production` |
| `QUICKBOOKS_CLIENT_ID`, `QUICKBOOKS_CLIENT_SECRET` | from the Intuit developer portal; required for live |
| `QUICKBOOKS_REDIRECT_URL` | must exactly match a redirect URI registered with Intuit |
| `QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN` | from the app's Webhooks page; leave empty to reject all webhooks |
| `TOKEN_ENCRYPTION_KEY` | base64 of 32 random bytes; changing it makes stored tokens unreadable, so reconnect afterwards |
